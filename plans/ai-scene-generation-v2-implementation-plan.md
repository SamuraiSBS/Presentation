# Новая AI система генерации редактируемых слайдов

## Статус документа

Этот документ является согласованным техническим планом. Он не означает разрешение на commit, push, deploy или изменение production. Перед реализацией нужно проверить текущее состояние рабочего дерева и сохранить все существующие пользовательские изменения.

## Цель

После утверждения текста выступления StudyDeck должен создавать тематические слайды визуального уровня референсов из `D:\presentation\референц слайдов`.

Обязательные свойства результата:

- содержание каждого слайда связано с соответствующим разделом речи;
- стиль всей презентации соответствует теме;
- композицию проектирует AI, а не шаблонный движок;
- сложный фон может оставаться одним растровым слоем;
- текст, основные изображения, плашки, цвета и диаграммы редактируются;
- пользователь сравнивает AI эскиз с редактируемой версией;
- утверждается именно редактируемая версия;
- команда `Переделать дизайн` меняет только выбранный слайд;
- первая версия работает в quality first режиме и может генерироваться 5–10 минут для шести слайдов.

## Согласованный пользовательский сценарий

```text
Тема и материалы
        ↓
Генерация текста выступления
        ↓
Пользователь редактирует и утверждает речь
        ↓
Фиксация точного содержания каждого слайда
        ↓
AI создаёт общую стилистику презентации
        ↓
AI генерирует художественный эскиз каждого слайда
        ↓
Эскиз преобразуется в редактируемую сцену
        ↓
Редактируемая сцена рендерится и проверяется
        ↓
Доска утверждения всех слайдов
        ↓
Утвердить или переделать отдельный слайд
        ↓
Открытие существующего редактора
        ↓
Экспорт в PPTX и PDF
```

После утверждения речи дизайн проход не имеет права менять текст выступления, факты и зафиксированный видимый текст.

## Почему текущая реализация не дала ожидаемый результат

Сейчас design review оборачивает прежний шаблонный генератор:

- первоначальный кандидат `v1` копирует уже построенный `slide.canvas`;
- preview отображает элементы этого canvas;
- AI redesign выбирает только один из существующих layout, image prompt и image strategy;
- генератор изображений создаёт отдельную иллюстрацию без текста, а не целый дизайн слайда;
- `canvas-builder` снова собирает слайд из заранее написанной композиции;
- новые презентации принудительно сводятся к теме `studydeckEditorial`;
- real E2E утверждает исходные варианты, но не проверяет визуальное качество.

То есть был реализован workflow утверждения, но не новый AI визуальный движок.

## Что сохраняем из прежней реализации

Полностью сохраняем:

- генерацию и пользовательское утверждение речи;
- `speakerNotes` и `speechScript` как канонический текст выступления;
- источники, фактологические проверки и quality gates;
- BullMQ, PostgreSQL, Redis и MinIO;
- cost envelope и учёт расходов;
- таблицы design review, версии кандидатов и optimistic revision;
- API утверждения и перегенерации одного слайда;
- существующий редактор объектов;
- `CanvasDiagramElement`;
- экспортные движки PPTX и PDF;
- обработку старых презентаций.

Текущий `packages/shared/src/presentation/canvas-builder.ts` сохраняется для старых проектов, demo, recovery и возможного дешёвого шаблонного режима. Для новой системы он не должен выбирать композицию.

Нельзя незаметно подменять неудачный AI слайд обычным шаблоном. Если новый движок не получил качественный результат, кандидат должен перейти в `failed` с понятной диагностикой.

## Новые контракты данных

Основные схемы добавляются в:

- `packages/shared/src/generation/schemas.ts`;
- `packages/shared/src/presentation/schemas.ts`;
- `packages/shared/src/projects/design-review.ts`.

### DeckStyleSpec

Одна стилистика на всю презентацию:

- палитра;
- фон и визуальная атмосфера;
- шрифтовая иерархия;
- стиль изображений и иконок;
- стиль плашек, линий и диаграмм;
- правила свободного пространства;
- разрешённые эффекты;
- запрещённые визуальные приёмы;
- текстовое описание темы для последующих генераций;
- версия стиля.

Для Солнечной системы модель может определить тёмный космический фон, холодные синие линии, жёлтые акценты для Солнца и реалистичные изображения планет. Эти значения нельзя хардкодить для всех тем.

### SlideContentLock

Контракт вычисляется из утверждённой речи и содержит:

- точный заголовок;
- главный тезис;
- короткие подписи и законченные предложения;
- числовые значения;
- подписи схем;
- данные диаграмм;
- допустимый список видимого текста;
- хеш содержания.

При `Переделать дизайн` content hash должен оставаться прежним.

### AiSceneSpec

Свободная сцена 1280×720:

- фон;
- текстовые элементы со ссылками на `SlideContentLock`;
- изображения;
- фигуры и плашки;
- иконки;
- соединительные линии;
- диаграммы;
- координаты и порядок слоёв;
- прозрачность;
- скругления;
- ограниченный набор теней и свечения, который поддерживают web, PPTX и PDF;
- группы элементов;
- семантическая роль каждого объекта.

Текстовый элемент должен ссылаться на ключ вроде `title`, `thesis`, `label:2` или `diagram.node:a`. При компиляции подставляется строка из `SlideContentLock`, а не распознанный текст изображения.

### CandidateQualityReport

Для каждого кандидата сохраняются:

- результат проверки текста;
- наличие дублирующего текста в фоне;
- визуальная релевантность речи;
- соответствие стилю презентации;
- безопасность геометрии;
- редактируемость элементов;
- результат сравнения эскиза и canvas;
- использованные модели;
- количество автоматических исправлений;
- длительность и стоимость этапов.

## Новый worker pipeline

Создать отдельный модуль:

```text
apps/worker/src/tasks/presentation/ai-scene/
  content-lock.ts
  style-director.ts
  concept-generator.ts
  scene-analyzer.ts
  layer-generator.ts
  scene-compiler.ts
  scene-quality.ts
  scene-repair.ts
```

### Этап A Фиксация содержания

`content-lock.ts` получает один раздел утверждённой речи и определяет, что зритель должен увидеть.

Перед сокращением текста определяется смысловая форма слайда:

- перечисление;
- сравнение;
- процесс;
- причинно следственная связь;
- определение;
- числовая диаграмма;
- вывод.

Результат должен состоять из коротких законченных формулировок. Нельзя механически брать начало речи или создавать фрагменты из нескольких слов.

### Этап B Общая стилистика

`style-director.ts` один раз анализирует тему, аудиторию, все разделы речи, источники и общий визуальный сюжет. Результат сохраняется в `DeckStyleSpec`.

Все слайды получают один художественный язык, но не одну композицию.

### Этап C Художественный AI эскиз

`concept-generator.ts` создаёт полный слайд 16:9, используя:

- `DeckStyleSpec`;
- речь конкретного слайда;
- точный сокращённый текст;
- данные диаграммы;
- роль слайда в общей истории;
- краткий контекст соседних слайдов.

Новый вызов должен генерировать целую композицию. Текущий prompt из `apps/worker/src/tasks/image-search.ts`, который запрещает текст и создаёт одну иллюстрацию, не используется для этого режима.

AI эскиз хранится в MinIO как самостоятельный артефакт. Он является визуальным ориентиром, а не финальным фоном.

### Этап D Анализ сцены

`scene-analyzer.ts` передаёт эскиз мультимодальной модели вместе с `SlideContentLock`.

Модель определяет:

- расположение текста;
- границы фоновой области;
- основные изображения;
- фигуры и плашки;
- связи схемы;
- визуальную иерархию;
- какие элементы нужно редактировать отдельно;
- какие детали можно оставить частью фона.

OCR не используется как источник текста. Даже если AI ошибся в буквах на эскизе, в canvas попадает правильная строка из content lock.

### Этап E Подготовка слоёв

`layer-generator.ts` создаёт:

- чистый тематический фон без текста;
- отдельные основные изображения;
- прозрачные декоративные изображения, когда это возможно;
- альтернативные ассеты для элементов, которые нельзя безопасно отделить от эскиза.

Правила первой версии:

- сложный фон можно хранить одним изображением;
- основное содержательное изображение желательно отделять;
- декоративные звёзды, текстуры и свечение можно оставить в фоне;
- текст нельзя запекать в финальный фон;
- диаграммы нельзя сохранять частью фонового изображения.

### Этап F Компиляция canvas

`scene-compiler.ts` превращает `AiSceneSpec` в существующий `SlideCanvas`.

Компилятор:

- не выбирает новый шаблон;
- сохраняет свободные координаты AI;
- подставляет точный текст;
- создаёт редактируемые диаграммы;
- ограничивает неподдерживаемые эффекты;
- проверяет границы и минимальные размеры текста;
- добавляет `origin: ai_scene_v2`.

`ensureEditableCanvas` должен распознавать этот origin и не перестраивать AI canvas обычным шаблоном.

## Автоматическая проверка и исправление

После компиляции worker рендерит редактируемый canvas в PNG. `scene-quality.ts` сравнивает исходный AI эскиз, рендер canvas, `SlideContentLock` и `DeckStyleSpec`.

Жёсткие проверки:

- весь видимый текст совпадает с `SlideContentLock`;
- в растровом фоне нет дублирующего текста;
- факты и значения не изменились;
- все элементы находятся в пределах слайда;
- текст читается;
- диаграмма имеет валидные данные;
- основное изображение существует;
- canvas открывается в редакторе и экспортируется.

Мягкие проверки:

- композиция соответствует эскизу;
- визуал объясняет речь;
- слайд соответствует стилю всей презентации;
- нет ощущения универсального шаблона;
- элементы не выглядят как случайная сетка интерфейсных карточек.

Разрешить не более одного автоматического repair прохода. После повторной неудачи кандидат получает статус `failed`. Бесконечные платные повторы запрещены.

## Хранение и миграция

Не изменять задним числом миграцию `20260908120000_design_review`. Добавить новую forward only additive migration.

В `DesignReview` добавить:

- `deckStyleSpec`;
- `designEngine`;
- `styleVersion`.

В `DesignReviewCandidate` добавить:

- `conceptObjectKey`;
- `renderedPreviewObjectKey`;
- `sceneSpec`;
- `contentHash`;
- `qualityReport`;
- `providerMetadata`;
- `engine`;
- `generationDurationMs`.

Поле `canvas` остаётся финальной редактируемой версией. Старые записи должны продолжать читаться без новых полей.

## API и перегенерация

Основные файлы:

- `apps/api/src/projects/projects.controller.ts`;
- `apps/api/src/projects/projects.service.ts`;
- `apps/web/src/app/api/projects/[id]/design-review/**`;
- shared request и response schemas.

Утверждение разрешается, только если кандидат готов, content hash совпадает, жёсткие quality gates пройдены, canvas существует и rendered preview относится к этому canvas.

`Переделать дизайн`:

- создаёт новую версию одного слайда;
- сохраняет `SlideContentLock`;
- сохраняет `DeckStyleSpec`;
- передаёт комментарий пользователя;
- создаёт новый AI эскиз;
- повторно собирает canvas;
- не меняет соседние слайды;
- не расходует бюджет всей презентации повторно.

## Доска утверждения

Обновить `apps/web/src/components/design-review-board.tsx`.

Для каждого слайда показывать:

- настоящую миниатюру;
- статус генерации;
- AI эскиз;
- редактируемый результат;
- переключатель или режим сравнения;
- список версий;
- краткий quality status;
- `Утвердить дизайн`;
- поле замечания;
- `Переделать дизайн`.

Кнопка утверждения относится только к редактируемому результату.

Во время генерации показывать этапы:

- создаём визуальную идею;
- разбираем композицию;
- готовим изображения;
- собираем редактируемый слайд;
- проверяем результат.

После утверждения всех слайдов открывается существующий редактор. Повторная финальная сборка не требуется: canvas уже готовы.

## Редактор и экспорт

Обновить поддержку AI сцен в:

- `apps/web/src/components/project-editor/editor-canvas.tsx`;
- `apps/web/src/components/project-editor/advanced-properties-panel.tsx`;
- `apps/worker/src/tasks/export/pdf-canvas.ts`;
- `apps/worker/src/tasks/export/pptx-canvas.ts`.

Первая версия должна позволять:

- менять весь текст;
- двигать и масштабировать элементы;
- заменять основные изображения;
- заменять или тонировать фон;
- менять цвета фигур;
- менять подписи схем;
- менять данные диаграмм;
- экспортировать тот же дизайн в PPTX и PDF.

Внутренние цвета сложного растрового фона отдельно не редактируются. Пользователь может заменить фон, изменить прозрачность или применить цветовой overlay.

## Время стоимость и очереди

Добавить отдельные cost envelope buckets:

- `style_direction`;
- `slide_concept`;
- `scene_analysis`;
- `layer_generation`;
- `scene_repair`.

Ограничения quality first версии:

- один стиль на презентацию;
- один основной concept проход на слайд;
- не более одного repair прохода;
- не более двух одновременно создаваемых слайдов;
- отмена устаревшей задачи при изменении revision;
- отсутствие скрытых повторов после provider timeout;
- целевое время для шести слайдов 5–10 минут.

На первом этапе стоимость измеряется. Оптимизация начинается после достижения нужного визуального качества.

## Эталонная приёмка

Главный acceptance fixture:

- `D:\presentation\референц слайдов\Солнечная_система_текст_выступления_2.docx`;
- изображения `1.png`–`6.png` из этой же папки.

Референсы задают уровень качества, а не требуют буквального копирования.

### Первый stop go этап

Сначала реализуются только слайды 1 и 2:

- общая стилистика;
- один свободный информационный слайд;
- один слайд с процессом или схемой;
- AI эскиз;
- редактируемый canvas;
- сравнение;
- редактирование;
- PPTX и PDF.

Если эти два слайда остаются шаблонными или существенно проигрывают референсам, дальнейшая интеграция останавливается и корректируется генератор. Не нужно сначала строить весь интерфейс, а потом обнаруживать, что визуальный принцип не работает.

### Полная приёмка шести слайдов

Результат считается принятым, если:

- все шесть слайдов соответствуют своим разделам речи;
- презентация имеет одну узнаваемую стилистику;
- используются несколько действительно разных композиций;
- нет случайного или бессмысленного декора;
- нет обрывков текста;
- нет дублирующего растрового и редактируемого текста;
- все основные текстовые элементы редактируются;
- основные изображения можно заменить;
- цвета фигур меняются;
- данные и подписи диаграмм редактируются;
- один слайд перегенерируется без изменения соседних;
- редактор показывает именно утверждённые версии;
- PPTX и PDF сохраняют композицию.

## Автоматические тесты

Добавить:

- shared тесты схем и content hash;
- тест запрета изменения текста при redesign;
- тест компиляции свободной сцены;
- тест сохранения `ai_scene_v2` без шаблонной пересборки;
- тест фонового слоя;
- тест диаграмм;
- тест budget reservation;
- worker тесты provider failure и repair limit;
- API тест optimistic revision;
- web тест сравнения AI эскиза и редактируемого результата;
- экспортные тесты новой сцены.

Real E2E должен:

1. Создать реальную шестислайдовую презентацию.
2. Проверить `engine === ai_scene_v2`.
3. Проверить concept и editable preview каждого слайда.
4. На одном слайде нажать `Переделать дизайн`.
5. Проверить, что content hash не изменился.
6. Проверить, что canvas и concept изменились.
7. Утвердить все слайды.
8. Открыть редактор.
9. Изменить текст, изображение и данные диаграммы.
10. Экспортировать PPTX и PDF.
11. Сохранить скриншоты шести слайдов для ручной визуальной оценки.

Зелёный E2E без визуальных артефактов не считается доказательством качества.

## Порядок реализации

1. Провести точную инвентаризацию текущего грязного рабочего дерева.
2. Не изменять и не откатывать существующие пользовательские файлы.
3. После отдельного разрешения пользователя оформить текущий design review код узкими коммитами.
4. Добавить shared контракты и новую Prisma migration.
5. Реализовать `SlideContentLock` и `DeckStyleSpec`.
6. Сделать платный prototype только для слайдов 1 и 2.
7. Получить визуальное подтверждение качества.
8. Реализовать scene analysis, layers и compiler для всех типов.
9. Расширить API и persistence.
10. Обновить доску утверждения.
11. Завершить editor и export parity.
12. Прогнать шесть слайдов Солнечной системы.
13. Проверить несколько принципиально разных тем.
14. Провести staging acceptance.
15. Production deploy выполнять только после отдельного явного разрешения.
