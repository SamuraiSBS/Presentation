# 07. Безопасные для пользователя повторы и release-проверка генерации

## Роль этого задания

Ты работаешь в `D:\presentation`, StudyDeck AI. Реализуй только этот пункт после планов 01–06. Сохрани все несвязанные пользовательские изменения. Не создавай новую архитектуру очередей и не заменяй BullMQ/React Query/существующие контракты.

Цель: будущая генерация либо становится полностью production-ready, либо остаётся в контролируемом состоянии восстановления. Пользователь не видит частичный deck, внутренние ошибки, провайдерские сообщения или «готовый» результат с нарушенными слайдами.

## Контекст продукта

Пользователь хочет быстро получить современную учебную презентацию на 7–10 минут и не встречать ошибки. Это не значит скрывать бесконечную поломку: система обязана автоматически выполнить ограниченное восстановление, сохранить введённые данные и показать спокойное понятное действие, только когда дальнейшее автоматическое восстановление исчерпано.

## Поведенческий контракт

### Статусы и видимые этапы

Зафиксируй понятные этапы, используя существующий progress contract или его безопасное расширение:

`research → story → narration → visual_fulfillment → building → repairing_layout → validating → saving → ready`.

- На UI показывай только короткие человеческие статусы по-русски, без технических причин.
- В `ready` можно перейти лишь после успешного прохождения всех блокирующих проверок из планов 01–06.
- Во время repair/retry не публикуй полуготовый документ как конечный и не разрешай скачать неподтверждённый export.

### Политика восстановления

Определи явную конечную матрицу retry/recovery, а не «catch и повторить всё»:

- временная ошибка сети/провайдера — используйте штатные ограниченные BullMQ attempts/backoff;
- factual/story/narration quality failure — детерминированная правка либо повтор только затронутого шага/слайда с лимитом;
- canvas/layout failure — сначала локальный безопасный recomposition и повторный audit;
- отсутствие documentary photo — уточнённый запрос и повтор поиска, затем согласованный fallback из плана 04;
- export для stale revision — не выдавать файл; предложить/запустить экспорт текущей ревизии существующим безопасным механизмом;
- непоправимый после лимитов случай — `failed`/recovery state без частичного ready и без потери prompt, sources, narration и подтверждённой версии.

Лимиты попыток, основания и итог должны быть структурированно зафиксированы для диагностики. Не делай бесконечные циклы и не повторяй дорогую генерацию целой презентации, если можно восстановить один слайд.

### Сообщение пользователю

- Не показывай raw `error.message`, stack trace, названия AI provider, schema/JSON, URL внутренних сервисов, ключи или идентификаторы очередей.
- При исчерпании восстановления показывай нейтральное: «Не удалось завершить подготовку презентации. Попробуйте ещё раз — ваши материалы и текст сохранены.»
- Если есть безопасная локальная причина, предложи конкретное пользовательское действие (например, повторить экспорт после редактирования), но не заставляй пользователя чинить внутренний баг.
- Сохраняй возможный готовый предыдущий revision как открываемый, но явно не подменяй им новую незавершённую генерацию.

## Что реализовать

1. Введи/уточни typed internal failure categories и единый mapping из worker/API в безопасный пользовательский status. Контракт не должен раскрывать приватные технические детали.
2. Установи транзакционные границы: job не отмечает проект `ready`, пока не сохранён и не проверен канонический document нужной ревизии.
3. Свяжи прогресс, число попыток и stage с структурированными Pino/Sentry событиями: project/job/revision, stage, duration, attempt, failure category, final disposition. Не логируй prompt/полные документы/секреты без необходимости; используй redaction.
4. Убедись, что API возвращает UI только безопасные поля, а React Query корректно опрашивает running/recovering состояния без мигания «готово/ошибка».
5. Ограничь retry на уровне correct scope и не нарушай idempotency/export request key.
6. Добавь release checklist/автоматизируемую smoke-проверку для реального generation pipeline, но не заставляй unit-тесты обращаться к внешнему AI, Tavily или сети.

## Обязательные тесты

1. Временная ошибка на первой попытке не переводит проект в `failed` или `ready` раньше времени; следующая успешная попытка завершается корректно.
2. Непройденный quality gate не может опубликовать `ready` revision.
3. Отсутствие фото инициирует только scoped recovery/fallback, а не падение всего job без причины.
4. После лимита пользовательский API payload не содержит raw provider/schema/stack error, а UI показывает нейтральный recovery CTA.
5. Stale export не возвращает устаревший файл и не смешивает ревизии.
6. Логи содержат нужные структурированные поля, но redaction не пропускает секреты/полные документы.
7. Предыдущая готовая версия остаётся доступна, когда новая генерация завершилась неуспешно.

## Release smoke-проверка

Подготовь воспроизводимую командную/ручную процедуру для staging/local окружения с реальными ключами, но оставь её env-gated:

1. Создать проект на 10 слайдов, принять narration и запустить генерацию.
2. Дождаться `ready` через API/job polling.
3. Проверить: число слайдов, 7–10 минут narration, source refs, documentary фото или разрешённые fallback, отсутствие запрещённых placeholder-фраз.
4. Открыть тот же проект в `http://localhost:3010` и убедиться, что editor показывает ту же ревизию.
5. Экспортировать PPTX и проверить revision/число слайдов/ключевые тексты.
6. Искусственно включить controlled failure test double и убедиться, что пользователь видит recovery, а не технический сбой.

Не включай внешние calls в стандартные Vitest runs; используй mocks или явный `RUN_LIVE_GENERATION_SMOKE=true`.

## Критерии приёмки

- Пользователь либо получает полностью валидную новую презентацию, либо безопасное понятное восстановление.
- Не существует пути, в котором broken document становится `ready` или скачиваемым export.
- Повторы ограничены, идемпотентны и направлены на минимальный повреждённый участок.
- Техническая причина остаётся в защищённой телеметрии, но не в интерфейсе.
- Проверки позволяют перед релизом убедиться, что редактор и экспорт согласованы.

В финальном отчёте перечисли: изменённые файлы, матрицу retry, безопасные UI-сообщения, результаты тестов, результат live smoke (если запускался) и известные environment-зависимые ограничения.
