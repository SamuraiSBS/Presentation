# Пакет промтов: качество будущих учебных презентаций

Этот каталог содержит восемь самостоятельных implementation-промтов для новых чатов Codex. Они подготовлены после аудита реальной презентации, созданной StudyDeck, и учитывают ответы владельца продукта.

## Зафиксированный продуктовый контекст

- Основная аудитория: школа, колледж и вуз.
- Типичная длительность выступления: 5-10 минут.
- Визуальный стиль: строгий учебный, без рекламной или развлекательной стилизации.
- На слайде должно быть мало текста, но смысл должен оставаться понятным без выступающего.
- Проверки качества не должны создавать пользователю новые препятствия, блокирующие экраны или необходимость разбираться с техническими ошибками.
- Исправления выполняются внутри generation/repair pipeline. Пользователь получает лучший валидный результат, а подробности остаются в структурированных логах.

## Что показал аудит

В тестовой презентации о Porsche 911 были обнаружены:

- перенос текста из посторонней темы про международный конфликт на слайды 1 и 11-14;
- расхождение между корректным текстом выступления и ошибочным видимым текстом слайдов;
- незаконченные фразы вроде `Porsche 911 показал.` и предложения, заканчивающегося на `в.`;
- повторение одинаковых тезисов и смысловых формул;
- только четыре слайда с фотографиями из четырнадцати для визуально богатой автомобильной темы;
- повторяющиеся композиции и узкие текстовые колонки;
- основной текст 16.5-18 pt, пограничный для проектора;
- корректное совпадение редактора с PPTX, то есть плохой контент экспортировался без дополнительной защиты.

Промты не должны зависеть от наличия исходного Porsche-файла. Каждый дефект должен быть превращён в компактный детерминированный fixture внутри тестов.

## Текущее состояние проекта, которое нельзя игнорировать

- `apps/worker/src/tasks/presentation.ts` является совместимым фасадом; реализация разнесена по `apps/worker/src/tasks/presentation/**`.
- Детерминированная критика и repair loop уже находятся в `apps/worker/src/tasks/presentation-quality.ts`.
- Финализация и сохранение принятого текста находятся в `apps/worker/src/tasks/presentation/quality/orchestration.ts`.
- `generatedText` является источником истины для принятой речи; после repair/fallback необходимо сохранять согласованные `speakerNotes` и `speechScript`.
- Планирование и design brief находятся в `apps/worker/src/tasks/presentation/planning/builders.ts` и `prompts/builders.ts`.
- Нормализация слайдов, layouts и design directions находится в `apps/worker/src/tasks/presentation/normalization/presentation.ts`.
- Изображения ищутся и сохраняются через `apps/worker/src/tasks/image-search.ts` и MinIO.
- Общие схемы и canvas находятся в `packages/shared/src/presentation/**`; публичный barrel `packages/shared/src/index.ts` нужно сохранять.
- Web использует `apps/web/src/lib/presentation-display.ts`; PPTX/PDF создаются в `apps/worker/src/tasks/export.ts`.
- Уже существуют quality dimensions, layout rhythm, mixed image strategy, `sceneTextMode`, premium themes и canvas parity. Новые изменения должны расширять их, а не создавать параллельный pipeline.
- OpenAI, Yandex и demo fallback должны остаться совместимыми; сетевые вызовы в тестах мокируются.
- Старые сохранённые презентации не мигрировать и не перерисовывать. Новые правила применяются к новой генерации и к безопасному export preflight.
- Пользовательские custom canvas нельзя переписывать автоматическим repair.

## Файлы-промты

1. `01-topic-relevance-and-silent-repair.md` - защита от текста из посторонней темы.
2. `02-slide-speech-semantic-alignment.md` - согласование речи и видимого текста.
3. `03-duplicate-and-fragment-control.md` - повторы, обрывки и шаблонные формулировки.
4. `04-educational-visual-plan-and-image-relevance.md` - визуальный план и релевантные изображения.
5. `05-readable-typography-and-layout-density.md` - читаемость, размеры текста и геометрия.
6. `06-export-preflight-and-format-parity.md` - предэкспортная проверка без блокировки пользователя.
7. `07-source-grounding-and-image-attribution.md` - источники, ссылки и авторство изображений.
8. `08-strong-educational-closing.md` - сильный итог вместо пустого `Спасибо за внимание`.

## Рекомендуемый порядок реализации

```text
01 -> 02 -> 03 -> 08 -> 04 -> 05 -> 07 -> 06
```

Причина: сначала устраняется смысловая порча и выравниваются источники текста, затем улучшаются визуалы и типографика, после чего общий export preflight проверяет уже завершённую систему.

Каждый файл самодостаточен и может быть реализован отдельно. Если реализация идёт не по порядку, новый чат обязан сначала проверить, какие соседние промты уже были внедрены, и адаптировать изменения к актуальному коду.

## Общие правила для всех новых чатов

- Сначала прочитать корневой `AGENTS.md`, выбранный промт и актуальные затрагиваемые файлы.
- Не переписывать завершённые соседние функции только ради архитектурной чистоты.
- Сохранять пользовательские изменения в грязном worktree.
- Делать repair-and-continue для исправимых проблем; фатальными оставлять только невозможность получить валидный по схеме документ или сохранить обязательные данные.
- Не добавлять пользовательские модальные окна, подтверждения качества или ручные чеклисты.
- Не выполнять remote deploy без отдельного запроса.
- Если пользователь просит применить изменения к `localhost:3010`, перестраивать только затронутые сервисы и дождаться финального `completed`, а не ограничиваться состоянием `building_slides`.
- После реализации проверять `git diff --check` и фактический staged scope перед commit, если commit был запрошен.

```powershell

npm run test -w @studydeck/shared
npm run test -w @studydeck/worker -- src/tasks/presentation-quality.test.ts
npm run test -w @studydeck/worker -- src/tasks/presentation.test.ts

npm run typecheck -w @studydeck/web

git diff --check
```
