# План-промт 01: стабильность UI и рабочие quality gates

Ты работаешь в монорепозитории StudyDeck AI по адресу `D:\presentation`.

Реализуй этот план полностью. Это уже утверждённое задание на изменение кода, а не просьба написать ещё один план. После короткого аудита живого репозитория переходи к исправлениям, тестам и локальной проверке. Задавай вопрос пользователю только при настоящем блокере или если требуется новое полномочие вне этого задания.

## Цель

Сделать основные frontend-сценарии StudyDeck надёжными перед дальнейшей декомпозицией:

- мастер создания презентации не ломается на узких экранах;
- мобильные просмотр и небольшие правки остаются полноценными;
- demo-маршруты редактора и экспорта не падают из-за конфигурации preview/API;
- ESLint снова является работающим quality gate;
- Playwright проверяет актуальный интерфейс, а не устаревшую разметку;
- в тестах есть явная защита от горизонтального переполнения и перекрытия основных кнопок.

Не редизайни продукт. Сохрани текущую тёплую оранжевую визуальную систему, Nunito, существующие компоненты, app chrome и простой редактор.

## Зафиксированный продуктовый контекст

- Основная аудитория: студенты и школьники.
- Продукт готовится к первым платным продажам в течение нескольких недель.
- Самая важная пользовательская претензия — качество содержания, поэтому UI-работа не должна затянуться в бесконечный редизайн.
- На телефоне приоритетны просмотр презентаций и небольшие правки.
- Полное создание презентации может оставаться desktop-first, но мобильная страница не должна физически ломаться.
- Метрики успеха: первые платежи, возвращаемость и качество презентаций.

## Текущий технический контекст

- Web: Next.js App Router в `apps/web`.
- Общие стили: `apps/web/src/app/globals.css` и `landing.css`.
- Мастер создания: `apps/web/src/components/new-project-form.tsx` и маршруты `/new`, `/projects/[id]/script`.
- Редактор: `apps/web/src/components/project-editor.tsx`, маршрут `/projects/[id]/editor`.
- Demo-данные и display-normalization находятся в `apps/web/src/lib/**`; найди фактические актуальные файлы перед изменениями.
- E2E: `e2e/*.spec.ts` и `playwright.config.ts`.
- Сейчас `playwright.config.ts` по умолчанию поднимает `npm run dev:web:fast` на `http://localhost:3020` с demo preview.
- В `apps/web/package.json` lint-скрипт всё ещё использует устаревший `next lint || eslint ...`.
- В корне установлен ESLint 9, но перед реализацией проверь наличие и состояние `eslint.config.*`.

## Перед началом

1. Полностью прочитай `AGENTS.md`, этот файл, `PRODUCT.md` и `DESIGN.md`, если последние существуют.
2. Выполни:

   ```powershell

   git -c safe.directory=D:/presentation diff -- apps/web e2e playwright.config.ts package.json
   ```

3. Не откатывай и не перезаписывай чужие незавершённые изменения.
4. Повтори базовые проверки и зафиксируй реальные, а не исторические сбои:

   ```powershell
   npm run lint
   npm run typecheck -w @studydeck/web
   npm run test -w @studydeck/web
   npm run test:e2e
   ```

5. Если полный E2E требует недоступной инфраструктуры, сначала запусти только относящиеся к заданию тесты. Не маскируй продуктовую ошибку как инфраструктурную и наоборот.

## Этап 1. Исправить узкий `/new`

Исследуй реальную DOM-структуру `new-project-form.tsx` и CSS-правила для `.new-page`, `.wizard`, `.wizard-main`, `.wizard-pane`, `.wizard-steps`, `.wizard-summary`, вариантов количества слайдов и основных кнопок.

Обязательное поведение на ширинах 320, 360, 390 и 412 px:

- отсутствует горизонтальный scroll у документа;
- ни один контейнер не шире viewport из-за `min-width`, фиксированной сетки, padding или длинного текста;
- текущий шаг и основной вопрос видны без наложения;
- кнопка продолжения доступна для клика и не перекрывается sticky/fixed-элементом;
- варианты выбора переносятся или переходят в одну колонку;
- summary не вытесняет основной шаг;
- safe-area нижней навигации учитывается;
- фокус клавиатуры остаётся видимым;
- на desktop существующая композиция не деградирует.

Не скрывай обязательные поля только ради прохождения теста. Не устанавливай `overflow-x: hidden` на весь документ как единственное исправление: сначала устрани источник переполнения.

Если мастер слишком сложен для полноценного мобильного создания, допустим компактный desktop-first notice. Но пользователь должен иметь возможность открыть страницу, понять ограничение и безопасно уйти к проектам; интерфейс не должен быть сломан. Если текущая форма уже легко адаптируется, предпочти рабочий компактный мастер вместо запрета.

## Этап 2. Проверить мобильные просмотр и небольшое редактирование

Проверь как минимум:

- `/projects/demo` или фактический demo-preview маршрут;
- `/projects/demo/editor`;
- навигацию между «Слайды», «Просмотр» и «Правки» в мобильном редакторе;
- редактирование заголовка/текста;
- замену изображения локальным файлом, если этот сценарий уже поддерживается;
- сохранение demo-изменения локально без реального API;
- отсутствие недоступных за нижней навигацией действий.

Не расширяй мобильный редактор до полного canvas-инструмента. Сохрани продуктовую модель: на телефоне — текст, изображение, просмотр и небольшие правки; точная геометрия остаётся расширенным desktop-сценарием.

## Этап 3. Устранить demo/editor и demo/export ошибки

Найди фактическую причину клиентских ошибок на demo-маршрутах при разных значениях `NEXT_PUBLIC_DEMO_PREVIEW`.

Требования:

- demo-preview в тестовом/dev-режиме использует согласованный источник demo-данных;
- production/real-API режим не должен случайно подменяться demo-данными;
- отсутствие проекта или API должно давать понятное error/empty state, а не необработанное исключение;
- `/projects/demo/editor` и `/projects/demo/export` должны стабильно работать в конфигурации Playwright;
- код не должен полагаться на случайно оставшийся dev server с другими env.

Не превращай все реальные ошибки API в demo fallback. Demo fallback разрешён только там, где он явно включён существующим продуктовым контрактом.

## Этап 4. Восстановить ESLint 9

Добавь корректный flat config на фактическом уровне монорепозитория. Перед выбором правил проверь текущие версии Next.js, TypeScript и установленных ESLint-пакетов.

Минимальные требования:

- `npm run lint` запускается без интерактивной настройки и без `next lint`;
- проверяются `.ts` и `.tsx` в `apps/**` и `packages/**` либо осознанно по workspaces;
- исключены `.next`, `dist`, coverage, Playwright artifacts и сгенерированные файлы;
- TypeScript/React/Next-правила не дублируются несовместимыми конфигами;
- нет массового отключения полезных правил ради зелёной команды;
- исправления существующих lint-ошибок ограничены безопасными и относящимися к задаче изменениями.

Если для качественной конфигурации недостаёт официального пакета, можно добавить минимально необходимую dev dependency. Не вводи альтернативный линтер.

Обнови workspace lint-скрипты так, чтобы они соответствовали flat config и актуальному Next.js 15.

## Этап 5. Актуализировать Playwright

Исправь тесты в `e2e/*.spec.ts` по текущему UI.

Правила:

- предпочитай `getByRole`, `getByLabel`, `getByTestId` и доступные имена;
- не выбирай неоднозначный заголовок только по тексту, если одинаковый текст есть в sidebar и main;
- не возвращай удалённый `.wizard-summary` лишь ради старого теста;
- `data-testid` добавляй только для стабильных продуктовых узлов, а не для каждой детали;
- проверяй результат пользовательского действия, а не внутреннюю реализацию;
- разделяй desktop и mobile ожидания, если UX намеренно различается.

Добавь целевые проверки:

1. `/new` на viewport `320x700`:
   - `document.documentElement.scrollWidth <= clientWidth`;
   - основная кнопка видима и реально кликабельна;
   - переход на следующий шаг происходит.
2. `/new` на Pixel 5 или эквиваленте.
3. Demo editor:
   - редактор открылся;
   - слайды видны;
   - простое изменение текста отражается в активном слайде.
4. Demo export:
   - workspace и действия экспорта отображаются без client exception.
5. Один keyboard smoke test:
   - Tab достигает основного действия;
   - focus-visible не пропадает.

Если в проекте нет axe-зависимости, не обязательно вводить её в этом пакете. Допустима небольшая Playwright-проверка семантики и фокуса. Если добавляешь `@axe-core/playwright`, ограничься ключевыми страницами и документируй осознанные исключения.

## Этап 6. Состояния интерфейса

Для затронутых страниц проверь четыре состояния:

- loading;
- empty;
- error;
- success.

Ошибки должны быть сформулированы для пользователя и содержать следующее безопасное действие: повторить, вернуться к проектам или открыть существующую презентацию. Не показывай сырой stack trace или внутренний API-текст.

Для визуальной проверки frontend используй предпочтительный workflow:

Проверяй `http://localhost:3020`. Не собирай Docker web только ради обычной frontend-проверки. `localhost:3010` требует production-container rebuild и нужен только если пользователь отдельно попросил production-like проверку.

## Критерии готовности

- `/new` не имеет горизонтального переполнения на 320–412 px.
- Основной CTA `/new` не перекрывается и работает мышью/тачем/клавиатурой.
- Desktop `/new` визуально не деградировал.
- Мобильные просмотр и небольшие правки работают без превращения редактора в полный canvas UI.
- Demo editor/export не падают в Playwright-конфигурации.
- `npm run lint` является реальной зелёной проверкой.
- E2E отражают текущий UX и проходят; тесты не «починены» возвратом устаревшей разметки.
- Добавлена автоматическая защита от повторного появления горизонтального overflow.
- Не изменены legacy `server.js`, корневые HTML/CSS/JS.
- Не добавлен `tsconfig.tsbuildinfo` или другой generated output.
