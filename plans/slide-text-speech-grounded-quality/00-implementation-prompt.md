# Реализация: качественный текст слайдов, строго основанный на речи

## Роль и границы задачи

Ты работаешь в репозитории StudyDeck AI, \`D:\\presentation\`. Реализуй систему
создания, проверки и безопасного исправления **видимого текста слайдов**.
Это задача для production-монорепозитория, а не для legacy MVP.

До изменения кода прочитай \`AGENTS.md\` в корне и действуй в соответствии с ним.
Работай только над данной задачей. Не меняй провайдеры, расчёт стоимости,
очереди, схему БД, UI вне необходимой доставки результата в редактор и
несвязанные незакоммиченные изменения.

### Обязательные решения владельца продукта

1. Единственный смысловой источник видимого текста конкретного слайда —
   соответствующий раздел принятой речи (\`speechScript\` /
   \`speakerNotes\` / раздел \`generatedText\`) **того же номера**.
2. Допускается краткая переформулировка и грамматическое сжатие речи. Нельзя
   добавлять новую мысль, факт, число, причинно-следственную связь, пример,
   вывод или утверждение из источника/плана, если они не прозвучали в этом
   разделе речи.
3. На слайде не должно быть «содержательного шума»: абстрактных, шаблонных
   или самоочевидных пунктов, которые создают видимость содержания, но не
   сообщают конкретную опору.
4. Разным типам слайдов нужны разные нормы текста. Не заполняй пункты до
   шаблонного числа: лучше один сильный тезис или меньше пунктов, чем
   «мусорный» текст.
5. Текстовая проблема не должна обрывать генерацию. После всех безопасных
   исправлений пользователь получает лучший безопасный вариант в редакторе,
   а не terminal failure из-за качества видимого текста. Не скрывай
   структурные, фактические, schema- или системные ошибки под видом
   текстового fallback.

### Пример продуктового правила

Речь: «Регулярная обратная связь помогает студенту замечать ошибки на раннем
этапе и корректировать стратегию обучения».

Недопустимые пункты сами по себе:

- «Ошибки выявляются раньше».
- «Стратегия обучения уточняется».
- «Обратная связь играет важную роль».

Они повторяют общий вывод без конкретного носителя смысла. Если в разделе
речи нет более конкретных фактов, механизма, условий, шагов, сравнения или
результата, не фабрикуй их: оставь один безопасный центральный тезис и
выбери компактную композицию.

Допустимые типы конкретной опоры: факт/число/дата/объект, определение
ключевого термина, механизм «что именно происходит», условие, ограничение,
следствие, этап процесса, решение, контраст или сравнение — но только если
это есть в речи данного слайда.

## Что есть в текущем коде

Сначала повторно проверь это по текущему checkout: рабочее дерево может
содержать чужие изменения, в том числе в целевых worker-файлах.

- \`apps/worker/src/tasks/presentation/planning/builders.ts\`:
  \`buildSlideTextPlans(...)\` строит \`SlideTextPlan\`. Сейчас он умеет
  подставлять \`sourceEvidenceForSlide(...)\`, \`plan.audienceQuestion\` и
  другие значения из narrative plan. Это не соответствует новой политике.
- \`packages/shared/src/generation/schemas.ts\` описывает \`SlideTextPlan\`.
- \`apps/worker/src/tasks/presentation/prompts/builders.ts\` передаёт
  \`slideTextPlans\` в prompt сборки документа. Проверь, что provider не
  получает инструкцию, разрешающую создать вторую историю.
- \`apps/worker/src/tasks/presentation-quality.ts\` содержит существующие
  проверки и fallbacks: \`findSlideSpeechAlignmentIssues\`,
  \`findGenericTextIssues\`, \`findLongSlideTextIssues\`,
  \`applyVisibleTextIntegrityFallbacks\`,
  \`applySlideSpeechAlignmentFallbacks\` и
  \`improvePresentationQuality\`.
- \`apps/worker/src/tasks/presentation/quality/orchestration.ts\` завершает
  документ через \`finalizeGeneratedPresentation(...)\` и
  \`repairReleaseCandidate(...)\`.
- \`apps/worker/src/tasks/presentation/providers/generation.ts\` связывает
  provider-ветки с планами текста и существующим ограниченным
  \`slide_text_repair\`.
- Основные текущие тесты находятся в
  \`apps/worker/src/tasks/presentation-quality.test.ts\`, а тесты planning/
  provider-веток — рядом с перечисленными модулями.

Не считай это описание доказательством текущего состояния: сначала сопоставь
его с исходниками и существующим diff.

## Целевой контракт

Для каждого слайда построй явную внутреннюю модель:

\`\`\`
accepted speech section N
  -> compact, grounded visible projection for slide N
  -> deterministic quality audit
  -> bounded local repair of that projection only
  -> best safe editor-ready slide N
\`\`\`

Видимая проекция включает все показываемые пользователю текстовые поля:
title, thesis, bullets, blocks, definition и текстовые подписи visual-элементов.
Не меняй принятую речь, \`generatedText\`, порядок \`speechScript\`,
source refs и пользовательский canvas ради красивого текста на экране.

### Нормы по типам

Используй существующие \`slideKind\`, \`layout\` и contract-систему; не
создавай параллельный набор произвольных типов. Внутри этой модели обеспечь:

| Тип / назначение | Безопасная видимая проекция |
| --- | --- |
| title | тема и при необходимости короткий подзаголовок из речи; без фиктивных bullets |
| content | заголовок, один центральный тезис, от 0 до 3 конкретных опорных пунктов |
| comparison | заголовок и только явно произнесённые стороны/критерии/контрасты |
| process/timeline | заголовок и 2–5 существующих в речи шагов/этапов в порядке речи |
| data/diagram | заголовок, ключевой вывод и подписи только для явно сказанных сущностей/значений |
| summary | один итог и 0–3 конкретных следствия из финального раздела речи |

Названия layout в репозитории могут отличаться: сопоставь таблицу с
реальными layout definitions. Не обязан искусственно менять layout, если
существующий умеет показать меньше элементов; если нужна замена, выбирай
только существующий компактный layout без подстановки нового текста.

### Что должно считаться дефектом

Добавь (или расширь без дублирования) детерминированную оценку качества,
которая на уровне поля и/или слайда обнаруживает:

- отсутствие содержательной опоры в речи данного слайда;
- перенос мысли из речи другого слайда;
- добавленный факт или смысл из source/narrative-plan/project prompt;
- общий шаблонный вывод без конкретного носителя смысла;
- повтор тезиса теми же словами в bullet, бессодержательный bullet и
  дублирование между видимыми полями;
- неподходящую плотность/число пунктов для slide kind/layout;
- обрыв, грамматический фрагмент, слишком длинное поле и несоответствие
  speechScript/speakerNotes принятой речи.

Не реализуй качество только чёрным списком русских фраз или lexical overlap.
Допустимы небольшие language-aware эвристики для отсева общих конструкций,
но положительное решение должно основываться на поддержке в section N и
наличии содержательной опоры. Поддержка не означает, что надо копировать
дословно: парафраза разрешена.

## Требуемая реализация

### 1. Безопасное построение проекции

- Переработай \`buildSlideTextPlans\` и связанные normalizers так, чтобы
  видимые title/thesis/bullets выводились из section N речи, а не из
  \`sourceEvidenceForSlide\`, \`audienceQuestion\`, \`slidePurpose\`,
  \`coreClaim\` или другого раздела как fallback.
- Narrative plan и sources могут использоваться только для **аудита
  происхождения** и выбора уже существующей структуры; они не являются
  текстовым донором, если фраза не поддержана речью N.
- Центральный тезис — наиболее содержательное утверждение раздела. Bullets —
  только неповторяющиеся конкретные опоры к нему. Их количество может быть
  нулевым.
- Никакой fallback не должен создавать формулу вроде «X важен»,
  «X помогает улучшить», «ошибки выявляются раньше» или «стратегия
  уточняется», когда он не может извлечь конкретную опору.

### 2. Аудит и исправление

- Сохрани и усили существующую проверку \`findSlideSpeechAlignmentIssues\`:
  она должна ловить не только почти полное тематическое расхождение, но и
  визуальный текст с низкой информационной ценностью.
- Сначала выполняй бесплатное локальное исправление: выбери/сожми
  качественные предложения только из речи N, убери слабые пункты, нормализуй
  композицию и пересобери generated canvas при необходимости.
- Если текущая architecture уже вызывает ограниченный provider repair,
  разреши ему только парафраз поддержанного текста N. В его input и prompt
  передай точный section N, затронутые поля, type/layout и запреты на новые
  факты. Обязательно проверь результат тем же детерминированным аудитом.
  Не добавляй новые самостоятельные provider-вызовы или retry-циклы.
- После неудачи модельного либо локального исправления предпочти безопасную
  деградацию: короткий заголовок + один поддержанный тезис и ноль слабых
  пунктов. Сохрани диагностический quality critique, но не меняй речь.
- Перед release повторно восстанови инварианты. Текстовые defects, которые
  уже преобразованы в безопасную малую проекцию, не должны превращаться в
  failed project. Нерешаемые schema/factual/source/canvas или provider
  ошибки должны вести себя как до этой задачи.

### 3. Редактор и экспорт

- Проверь, что уменьшение количества bullets, смена canonical blocks и
  regenerated canvas одинаково отображаются веб-редактором и экспортом.
- Не ломай возможность пользователя вручную редактировать уже готовый
  слайд. Никакой generation-time fallback не должен выполняться при
  последующем открытии, сохранении или экспорте существующей презентации.

## Тесты и доказательства

Добавь узкие, детерминированные Vitest-тесты. Не обращайся к настоящему AI,
Tavily, интернету, Docker или платным provider API.

Минимальные cases:

1. Обычный content-slide: план текста и итоговый slide берут содержание
   только из matching speech section, не из source excerpt/audience question.
2. Разрешённая парафраза сохраняет смысл конкретного предложения речи.
3. Слабые примеры («играет важную роль», «ошибки выявляются раньше»,
   «стратегия уточняется») отвергаются, если в речи нет конкретной опоры;
   slide безопасно остаётся с меньшим числом пунктов.
4. Конкретные механизм/условие/шаги из речи сохраняются как допустимые
   короткие пункты.
5. Нельзя перенести мысль между slide 1 и slide 2, даже когда тема общая.
6. Для title/content/summary и одного structure-heavy варианта проверяются
   собственные нормы плотности.
7. Local repair сохраняет \`generatedText\`, \`speakerNotes\`,
   \`speechScript\`, source refs и custom canvas там, где это гарантирует
   существующий контракт.
8. Лучший безопасный вариант с text-only defect проходит путь в editor-ready
   document и не становится terminal failure. Отдельно докажи, что
   schema/factual defect этим правилом не маскируется.
9. Existing quality, provider, renderer/export and accepted-narration tests
   остаются зелёными или их ожидания обновлены строго из-за нового
   продуктового контракта.

Не ослабляй тесты, не удаляй проверки качества и не закрепляй ложный успех
моками release gate. Тестируй фактическую \`productionQualityReleaseResult\`
или реальную завершающую цепочку, где это возможно без provider API.

## Порядок работы

1. Прочитай \`AGENTS.md\`; выполни \`git status --short\` и
   \`git diff -- <целевые файлы>\`.
2. Если незакоммиченные изменения другого автора перекрывают нужные строки,
   не затирай и не форматируй их. Сообщи о конфликте и остановись с
   точными файлами/hunks; не решай конфликт предположениями.
3. Кратко опиши найденный путь \`speech -> plan -> provider output ->
   quality -> release\` и предлагаемый минимальный diff.
4. Реализуй узкий change-set, предпочитая существующие schemas, helpers,
   quality orchestration и test conventions.
5. Запусти сначала затронутые worker Vitest-файлы и worker typecheck; затем
   пропорциональные расширенные проверки. Исправляй только проблемы,
   относящиеся к задаче.
6. Не запускай платную генерацию, не выполняй Docker rebuild/redeploy и не
   делай коммит без отдельного разрешения владельца.
7. В финале верни: список файлов, краткое объяснение логики, команды и
   результаты тестов, список не проверенного runtime и готовый следующий
   шаг для отдельной авторизации.

## Условия приёмки

Работа готова только если:

- видимый текст каждого нового слайда ограничен смыслом его речи;
- разрешённый парафраз не меняет фактический смысл;
- filler не используется для заполнения списка;
- нехватка содержательных опор уменьшает текст, а не вызывает выдумку;
- текстовый дефект не ломает доступ пользователя к готовой презентации;
- существующие речь, источники, пользовательский canvas и непричастные
  изменения сохранены;
- это доказано детерминированными тестами, без платных вызовов.
