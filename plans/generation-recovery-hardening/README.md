# StudyDeck: надёжная генерация без видимых пользователю ошибок

Этот пакет превращает текущую цепочку создания презентации в управляемый recovery-процесс: пользователь получает только реальный AI-текст, реальные источники и готовую презентацию, а временный сбой провайдера обрабатывается внутри системы ограниченным повтором или локальной сборкой из уже принятых артефактов.

## Главная продуктовая цель

После нажатия «Создать презентацию» пользователь не должен видеть техническую ошибку генерации. Система может повторить безопасный шаг или собрать презентацию заново из уже проверенных реальных данных, но не имеет права подменять результат demo-текстом, выдуманными ссылками либо бесконечно тратить деньги.

Результат считается готовым, только если одновременно есть:

- реальный текст от настроенного AI-провайдера, а не demo/mock/fallback prose;
- реальные источники из поиска, привязанные к презентации и с проверяемыми URL;
- согласованные текст слайдов, заметки докладчика и script/speech;
- валидная презентация с layout/visual metadata и источниками на слайдах или в общем списке;
- прозрачный фактический расход в рублях по каждому этапу и общий жёсткий лимит на один запуск пользователя.

## Непереговорные инварианты

1. Не использовать `ALLOW_DEMO_GENERATION`, demo-preview или синтетические источники для production generation. Реальные AI и Tavily вызовы разрешены только в Prompt 03.
2. После успешного поиска сохранять и повторно использовать snapshot источников. Повторная сборка презентации не должна запускать Tavily заново.
3. После принятия полного текста выступления он является первичным артефактом: fallback не может его укорачивать, заменять шаблонными фразами или создавать фиктивную речь.
4. Повторные presentation jobs одного пользовательского запуска разделяют один расходный лимит. Новый job не является разрешением создать новый независимый budget envelope.
5. Ретраи ограничены, детерминированы и наблюдаемы. Когда остатка бюджета или числа разрешённых попыток нет, система использует локальную сборку из принятых артефактов; она не запускает новый платный вызов молча.
6. Локальный fallback допустим только как рендеринг уже принятого реального содержания. Он не является способом обойти source, narration, template-phrase или production-quality gates.
7. Не удалять и не откатывать чужие изменения. В частности, не трогать историческое состояние `.audit-bmw/tmpw120oeib/enlarged.pptx`.

## Последовательность чатов

Все numbered prompts выполняются строго последовательно, каждый — в отдельном новом implementation-чате Codex. Не запускайте их параллельно: они затрагивают общие worker/API contracts и один и тот же recovery flow.

1. `01-project-budget-and-source-reuse.md` — единый лимит запуска, идемпотентные retrуies и reuse источников.
2. `02-local-presentation-recovery.md` — надёжная финальная сборка из принятой речи и источников, без demo и деградации текста.
3. `03-one-real-end-to-end-proof.md` — ровно один разрешённый платный live-прогон и доказательство полного пути.
4. `04-final-commit-readiness.md` — независимая read-only проверка всего принятого diff и evidence перед коммитом.
5. `05-commit-and-post-commit-smoke.md` — узкий коммит принятого набора и неплатная post-commit проверка.
6. `06-optional-remote-deploy.md` — явный remote deploy принятого commit SHA и production smoke без новой генерации.

`00-read-only-coordinator.md` предназначен для одного постоянного coordinator-чата. Он ничего не меняет: проверяет отчёты и текущий diff, решает, можно ли переходить к следующему prompt, и формирует точный follow-up при отказе.

После Prompt 05 пакет завершён для локальной разработки. Ничего из Prompt 01–03 повторять не нужно: единственный платный E2E-прогон уже является доказательством результата. Prompt 06 запускается только после отдельного явного разрешения пользователя на remote deploy с указанными host, remote path и public URL.

## Общие границы для каждого implementation-чата

- Работать только в `D:\presentation`; до правок полностью прочитать `AGENTS.md`, этот `README.md` и текущий numbered prompt.
- До любых изменений выполнить `git status --short` и сохранить чужие изменения.
- Не делать `git add`, commit, push, deploy, reset, checkout, clean, миграции или Docker rebuild/restart без явного разрешения именно этого prompt.
- Не добавлять зависимости и не менять legacy MVP в корне.
- Не переходить самостоятельно к следующему prompt. После собственного отчёта остановиться.
- По умолчанию сетевые AI/search вызовы запрещены. Единственное исключение — Prompt 03, после принятия двух предыдущих этапов координатором.

## Требования к отчёту исполнителя

Каждый implementation-чат заканчивает работу одним самодостаточным отчётом:

1. что изменено и почему;
2. полный список изменённых файлов;
3. доказательство каждого acceptance criterion;
4. команды проверки и их точный результат;
5. текущий `git status --short`, с отделением своих изменений от ранее существовавших;
6. известные риски или блокеры без маскировки;
7. фактический расход в рублях по этапам — только при Prompt 03; при остальных prompts указать `0 RUB: внешние AI/Tavily вызовы не выполнялись`.

## Что прикладывать между чатами

В coordinator-чат всегда передавайте полный отчёт завершившегося implementation-чата. Для следующего implementation-чата прикладывайте только:

- этот `README.md`;
- соответствующий numbered prompt;
- последний принятый отчёт координатора;
- полный отчёт предыдущего этапа, если он есть.

Не прикладывайте все prompts сразу и не разрешайте чату расширять scope «по пути».
