# 03 — один реальный E2E-прогон с учётом стоимости

## Разрешение и цель

Этот prompt можно запускать только после того, как coordinator-чат явно принял Prompt 01 и Prompt 02. Он разрешает ровно **один** новый платный live-run в локальном StudyDeck: реальный AI-текст, реальный Tavily source search и переход от создания проекта до готовой презентации.

Цель не в повторных попытках «пока не получится», а в доказательстве, что после hardening один пользовательский запуск контролирует расход, сохраняет реальные источники/текст и завершает проект без видимой технической ошибки.

## Строгие лимиты

- Создать не более одного нового тестового проекта и не более одного user-visible generation run.
- Не делать второй платный запуск, даже если первый неудачен. При неудаче остановиться, сохранить project/job IDs, фактический расход и evidence для coordinator-чата.
- Использовать только реально настроенные AI provider и Tavily. `ALLOW_DEMO_GENERATION` и любые demo/mock branches запрещены.
- Не менять код, contracts, миграции, provider keys или cost cap в этом prompt. Это verification-only этап.
- Не делать commit, push или remote deploy.

## Перед запуском

1. Прочитай `AGENTS.md`, README пакета, два принятых отчёта и решение координатора.
2. Проверь текущий `git status --short` и что рабочие контейнеры/сервисы действительно содержат принятый код; при необходимости разрешено узко пересобрать только затронутые локальные `api`/`worker` сервисы по AGENTS.md. Не перестраивай web без необходимости.
3. Проверь, что API health, worker, Redis/Postgres/MinIO доступны. Не раскрывай секреты из `.env` в отчёте.
4. Зафиксируй до запуска cap, базовый zero/начальный usage и конфигурацию provider/model только в безопасном виде (имя, без ключа).

## Прогон

Создай один обычный проект с достаточно конкретной учебной темой и включёнными источниками. Пройди нормальный путь приложения: создание проекта, поиск источников, генерация речи/содержания, проверка/принятие автоматического результата, постановка/обработка presentation job и ожидание финального состояния.

Не подменяй процесс записью прямо в БД. Допустимы существующие внутренние API/тестовые helpers только если они отражают реальный пользовательский workflow и позволяют достоверно связать созданный проект, jobs и usage.

## Что доказать по итогам

Для единственного созданного project ID собери evidence:

1. Финальный статус `ready`, отсутствие user-visible технической ошибки и валидная готовая презентация.
2. Реальный AI provider/model использован для текста; нет demo/mock markers.
3. Есть реальные Tavily/WEB источники: не менее требуемого политикой числа, с настоящими URL и source refs в итоговой presentation.
4. Реальная речь/заметки/slide text согласованы по contract; нет очевидной подмены generic/template text. Проверь сохранённые quality diagnostics.
5. Итоговая презентация имеет ожидаемое число слайдов и проходит доступные structural/canvas/export-parity проверки.
6. Все cost events сгруппированы в один attempt group/envelope lineage. Покажи фактический расход по этапам, например: Tavily sources, narration, design/repair, presentation, локальный fallback (если был), и итог.
7. Сравни итог с cap: `sum(actual settled usage) <= run cap`. Не выдавай estimate за факт. Если телеметрия не даёт точную цену конкретной операции, пометь её как estimate и отдельно покажи доступный фактический ledger.

## Формат стоимости

В отчёте используй таблицу:

| Этап | Provider/model | Фактический расход, RUB | Evidence |
|---|---|---:|---|

После таблицы: `Итого фактически: X RUB; лимит запуска: Y RUB; остаток: Z RUB.`

Если первый live-run упал, таблица всё равно обязательна. Честный результат в этом случае — `не пройден`, без второго платного прогона.

## Отчёт и остановка

Передай coordinator-чату: project ID, job IDs, безопасные статусы и diagnostics, вывод health/worker checks, перечень источников с URL, результаты quality checks, query/output cost ledger без секретов и текущий `git status --short`.

После отчёта остановись. Не исправляй код, не делай второй запуск и не начинай commit/deploy.
