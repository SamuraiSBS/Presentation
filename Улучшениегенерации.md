# Задача: убрать лишний клик после подтверждения текста презентации

## Контекст

Проект: StudyDeck AI, монорепозиторий `D:\presentation`.

Текущий пользовательский flow примерно такой:

1. Пользователь создает проект / задает тему / загружает материалы.
2. Система генерирует текст/сценарий презентации.
3. Пользователь видит текст презентации перед созданием слайдов.
4. Пользователь подтверждает текст.
5. Сейчас после подтверждения может требоваться лишнее действие для запуска финальной генерации.

Нужно сохранить просмотр и подтверждение текста пользователем, но после подтверждения сценария финальная генерация презентации должна запускаться автоматически.

## Цель

Сделать flow:

```text
Создать проект
-> сгенерировать текст презентации
-> показать текст пользователю
-> пользователь нажимает "Подтвердить"
-> автоматически запускается генерация слайдов
-> пользователь видит прогресс
-> после готовности открывается редактор презентации
```

Пользователь НЕ должен после подтверждения текста нажимать дополнительную кнопку вроде "Создать презентацию", "Запустить генерацию", "Продолжить" и т.п.

## Важно

Не нужно делать полностью blind autopilot без просмотра текста.

Пользователь обязательно должен видеть и подтверждать текст презентации до создания слайдов.

Autopilot нужен только после подтверждения текста: подтверждение становится единственным действием, которое запускает финальную генерацию.

## Что изменить

### 1. Найти текущий narration/script review flow

Исследовать:

- `apps/web`
- `apps/api`
- `apps/worker`
- `packages/shared`
- Prisma schema/migrations при необходимости

Особенно проверить:

- route страницы просмотра сценария, вероятно `/projects/[id]/script`;
- endpoint подтверждения/сохранения narration draft;
- endpoint запуска final generation;
- project/job statuses вроде `script_queued`, `script_ready`, `script_accepted`, `generating`;
- web-компоненты с кнопками подтверждения текста и запуска генерации.

### 2. Изменить frontend flow

На странице просмотра текста презентации:

- оставить возможность увидеть текст;
- оставить возможность отредактировать текст, если она уже есть;
- оставить одну основную кнопку подтверждения, например "Подтвердить";
- после успешного подтверждения автоматически запускать final generation;
- не показывать отдельную вторую кнопку запуска генерации;
- после запуска переводить пользователя на экран прогресса или текущий project page с progress state;
- после готовности презентации открыть редактор.

Если сейчас есть две кнопки:

```text
Подтвердить текст
Создать презентацию
```

нужно оставить только одну:

```text
Подтвердить и создать
```

или, если продуктово лучше:

```text
Подтвердить
```

Но действие кнопки должно включать и подтверждение, и запуск генерации.

### 3. Изменить API orchestration

После подтверждения текста API должен автоматически ставить job финальной генерации.

Варианты реализации:

- либо endpoint `PATCH /projects/:id/narration` после сохранения accepted draft сам enqueue-ит generation job;
- либо web после успешного подтверждения вызывает existing generate endpoint автоматически без участия пользователя;
- предпочтительнее сделать это на backend/API стороне, чтобы flow был надежным и не зависел от поведения клиента.

Нужно избежать двойного запуска generation job при повторном клике/refresh.

Добавить идемпотентность:

- если final generation job уже queued/running, не создавать дубль;
- если presentation уже generated/ready, вернуть текущий статус;
- если script не accepted, не запускать final generation.

### 4. Worker logic

Worker должен остаться ответственным за качество генерации.

При финальной генерации:

- использовать подтвержденный пользователем текст как основу;
- не требовать дополнительных пользовательских действий;
- repair/quality/fallback logic должен работать автоматически;
- repairable проблемы не должны превращаться в user-facing failure.

Особенно важно:

- если на слайде мало предложений;
- если layout требует больше контента;
- если слайд слабый;
- если часть visual/image search не сработала.

Такие случаи нужно чинить внутри worker через repair/fallback, а не останавливать процесс для пользователя.

Фатальные ошибки можно показывать пользователю только если:

- AI provider недоступен после retries;
- нет API key / quota / лимиты;
- не удалось обработать материалы;
- БД/Redis/MinIO недоступны;
- результат невозможно привести к shared schema после всех попыток repair/fallback.

### 5. Обновить статусы и тексты прогресса

Во frontend показывать спокойные пользовательские статусы:

- "Готовим текст презентации"
- "Ожидаем подтверждения"
- "Создаем слайды"
- "Улучшаем качество"
- "Готовим редактор"

Не показывать пользователю внутренние причины вроде:

- `layoutHasEnoughContent failed`
- `too few sentences`
- `repair attempt failed`
- raw schema/provider errors

### 6. Убрать лишние CTA

Найти и убрать/скрыть лишние кнопки после подтверждения текста:

- "Создать презентацию"
- "Запустить генерацию"
- "Продолжить"
- любые CTA, которые требуют второго клика после accepted narration.

После подтверждения пользователь должен сразу попасть в состояние ожидания генерации.

### 7. Тесты

Добавить или обновить targeted tests:

- подтверждение текста запускает final generation job автоматически;
- повторное подтверждение не создает duplicate job;
- если generation job уже queued/running, API возвращает актуальный статус;
- web после подтверждения не показывает вторую кнопку запуска;
- web показывает progress state после подтверждения;
- финальная генерация использует accepted narration;
- repairable slide/content issues не становятся user-facing failure;
- fatal errors отображаются пользователю коротко и понятно.

### 8. Проверка вручную

Проверить flow локально:

1. Открыть создание презентации.
2. Создать проект.
3. Дождаться текста презентации.
4. Убедиться, что текст виден пользователю.
5. Нажать кнопку подтверждения.
6. Убедиться, что без второго клика началась генерация слайдов.
7. Дождаться готовности.
8. Убедиться, что открыт редактор презентации.

## Acceptance Criteria

- Пользователь видит текст презентации до создания слайдов.
- Пользователь подтверждает текст одним действием.
- После подтверждения финальная генерация запускается автоматически.
- Нет дополнительной кнопки/шага после подтверждения.
- Повторный клик/refresh не создает дублирующий generation job.
- Repairable ошибки генерации не показываются пользователю как остановка процесса.
- Фатальные ошибки показываются только в крайних случаях.
- Тесты обновлены под новый flow.
